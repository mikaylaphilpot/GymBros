# GymBros

GymBros is a MERN web application with a planned Flutter mobile client. The
backend includes the Express API scaffold, MongoDB configuration, and push
notification endpoints.

## Backend database configuration

Create a local `backend/.env` file with your MongoDB connection string:

```text
MONGODB_URI=<local or remote MongoDB connection string>
```

`backend/.env` is ignored by Git. Keep real credentials there locally, or configure `MONGODB_URI` as an environment variable in your deployment environment. Never commit the real connection string.

## Backend development

Run these commands from `backend/`:

```powershell
npm install
npm test
npm start
```

The backend uses port `5001` by default. Set `PORT` to use another port.

Do not commit `.env`, VAPID keys, MongoDB credentials, JWT secrets, or real
push subscription data.

## Push notifications: current development testing

The notification API currently supports:

- `POST /api/notifications/subscribe` - save or replace a user's browser push
  subscription.
- `POST /api/notifications/send` - send a notification to a subscribed user.

Until JWT authentication is connected, local development can identify a user
with the `x-user-id` header. Enable this only locally:

```text
ALLOW_DEV_USER_HEADER=true
```

In production, the header must be disabled and `req.user` must come from the
real JWT authorization middleware.

### 1. Configure local push delivery

From `backend/`, generate VAPID keys:

```powershell
npx web-push generate-vapid-keys
```

Put the generated values in a local, uncommitted `backend/.env` file:

```text
VAPID_PUBLIC_KEY=<public key>
VAPID_PRIVATE_KEY=<private key>
VAPID_SUBJECT=mailto:developer@example.com
ALLOW_DEV_USER_HEADER=true
```

For persistent subscriptions, also configure:

```text
MONGODB_URI=<local or remote MongoDB connection string>
MONGODB_DB=gymbros
```

Without `MONGODB_URI`, development uses an in-memory store. All subscriptions
are lost when the server stops.

Start the API:

```powershell
cd backend
npm start
```

### 2. Create a real browser subscription

Push subscriptions cannot be invented in Postman. The `endpoint`, `p256dh`,
and `auth` values must be generated by a browser through
[`src/utils/pushNotifications.ts`](src/utils/pushNotifications.ts).

The frontend must provide:

```text
VITE_VAPID_PUBLIC_KEY=<same public key as the backend>
VITE_API_BASE_URL=http://localhost:5001
```

Call `subscribeToPushNotifications(token)` from a browser served over HTTPS
or from `localhost`. Grant notification permission. The utility registers
[`src/public/service-worker.js`](src/public/service-worker.js), creates the
browser subscription, and saves it through the subscribe endpoint.

### 3. Test the API in Postman

Save a subscription:

```http
POST http://localhost:5001/api/notifications/subscribe
Content-Type: application/json
x-user-id: user-1
```

```json
{
  "subscription": {
    "endpoint": "https://push-service-provider.example/...",
    "expirationTime": null,
    "keys": {
      "p256dh": "<value copied from the browser subscription>",
      "auth": "<value copied from the browser subscription>"
    }
  }
}
```

Expected response: HTTP `201`.

Send a notification:

```http
POST http://localhost:5001/api/notifications/send
Content-Type: application/json
x-user-id: sender-1
```

```json
{
  "targetUserId": "user-1",
  "messageText": "Your GymBros workout is starting!",
  "title": "Workout Reminder",
  "url": "/workouts"
}
```

Expected response: HTTP `200`, followed by a browser notification. Confirm
that the notification click opens or focuses the requested URL.

Useful negative cases to test in Postman:

- Missing `x-user-id` -> HTTP `401`.
- Missing or malformed subscription -> HTTP `400`.
- Unknown `targetUserId` -> HTTP `404`.
- Expired provider subscription -> HTTP `410`, and the subscription is
  removed.

The automated notification route tests can be run with:

```powershell
cd backend
npm test
```

## Push notifications: testing when the application is complete

When authentication, the React web app, MongoDB, and deployment are ready,
replace the development header flow with JWT authentication and test the
complete user journey:

1. Register two test accounts and verify their email addresses.
2. Log in as the recipient and confirm the frontend receives and stores a
   browser subscription using the recipient's JWT.
3. Confirm the subscription is persisted in the test MongoDB database and is
   replaced safely when the same user subscribes again.
4. Log in as the sender and send a notification to the recipient through the
   authenticated API.
5. Confirm the notification title, body, icon/badge behavior, target URL, and
   notification-click focus behavior.
6. Confirm a sender cannot impersonate another user by changing headers,
   tokens, or request fields.
7. Revoke browser notification permission and verify the API handles an
   invalid subscription by deleting it and returning the documented status.
8. Repeat the flow from a deployed HTTPS domain in supported browsers.
9. Verify that MongoDB contains no duplicate active subscription records for
   the same user and that secrets are absent from logs and responses.

The completed test suite should include:

- Unit tests for subscription validation, upsert behavior, payload defaults,
  and expired-subscription cleanup.
- Route integration tests for authentication failures, validation failures,
  successful subscribe/send operations, missing recipients, and provider
  errors.
- Authentication tests proving that only valid JWTs can subscribe or send.
- MongoDB integration tests using an isolated test database.
- Browser tests covering permission handling, service-worker registration,
  notification display, and notification-click navigation.
- Deployment smoke tests against the HTTPS staging environment before
  production.

The Postman collection used for the final demonstration should use variables
for the base URL, JWTs, user IDs, and test subscription values. Never store
real credentials or private VAPID keys in the collection.
